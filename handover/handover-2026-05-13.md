## Key Decisions & Rationale

### gpt-realtime-translate API 仕様への対応（PR #29）
- **format パラメータ送信を削除**: `audio.output.format: "pcm16"` は API 未対応で session.update 全体が拒否される。サーバデフォルトに任せる。
- **`audio.input.transcription.model: "gpt-realtime-whisper"` 明示指定**: 公式 Cookbook 通り。これがないと `session.input_transcript.*` イベントは送られない。
- **原文と翻訳を独立ストリームとして UI 表示**: API は両者を別レートでストリーミング（原文は短い単位で頻発、翻訳はまとまった単位で遅延）するため、ペアリング設計は破綻する。

### スレッド安全性（PR #34、codex セカンドオピニオン反映）
- **frozen dataclass + Lock スナップショット方式採用**: queue.Queue は consumer が最新値だけ欲しい設計で溜まる懸念、プリミティブごとの atomic では複数フィールドの混在リスク → combined struct がベスト。
- **後方互換プロパティで透過化**: `audio_peak` / `gain_mode` 等の既存属性アクセスを維持。app.py / RPC は無変更で動作。
- **capture loop の最適化**: 冒頭で 1 回 snapshot 取得し計算、末尾で 1 回 atomic 更新（Lock 取得は数十Hz、NumPy 処理 >1ms に対して negligible）。

### プリロード lifecycle（PR #36）
- **早期キャンセルチェック**: thread 起動 → `prepare()` 開始までの間にキー変更されたら重い処理を呼ばずに撤退。
- **`_classify_preload_cache` pure function 切り出し**: `("ok"/"stale"/"miss", system)` 3 状態に分類。テスト容易性向上。
- **`_recorder=None` を stale として明示 shutdown**: 旧実装は参照を None に書き換えるだけで shutdown 漏れていた。

### API キー判定強化（PR #35）
- **厳格な regex は避けて長さ + プレフィックスチェック**: 将来の形式変更で破綻するリスクを避け、最低限の検証に留める。
- **プレースホルダー除外**: "xxx" / "your-" / "placeholder" を含むキーは無効扱い。

### テストインフラ改善（PR #32, #33）
- **動的ポート割り当て**: TIME_WAIT 状態のポート競合が flaky の真因。`_get_free_port()` で各テスト毎に OS から払い出し。
- **テスト API キー命名統一**: `.gitleaks.toml` allowlist の `sk-test-fake-*` パターンに揃えて再発防止。

## Blockers, Gotchas & Workarounds

### gpt-realtime-translate API は session.update に厳密
- 未対応パラメータがあると全体拒否、`session.updated` が来ないので一見気付きにくい
- 確認方法: verbose ログの `RT_ERROR` で `Unknown parameter` を確認

### Input transcription はデフォルト OFF
- `audio.input.transcription.model: "gpt-realtime-whisper"` 明示指定必須
- 参照: <https://developers.openai.com/cookbook/examples/voice_solutions/realtime_translation_guide>

### 原文・翻訳のストリーム独立
- API は短い単位の原文と、まとまった単位の翻訳を別レートで送信
- UI は 1:1 ペアリングではなく独立行表示で対応（`broadcast("", text)` / `broadcast(text, "")`）

### gitleaks の DeepL 形式検出
- テスト fixture で UUID 風文字列を使うとき、最初の 8 文字に 16 進数外（例: `g`）を入れて regex `[0-9a-f]{8}` を回避

### gitleaks allowlist regex の境界
- `sk-test-fake-[A-Za-z0-9]+` はハイフン非対応 → サフィックスは連結形式（例: `deltadone`）

### CaptionSystem.__init__ をバイパスしたモック生成
- 重い依存（OpenAI クライアント、設定読込）を避けるため、`object.__new__(CaptionSystem)` で生成 + 最小限の属性初期化
- スレッド安全性テストで採用

## Key Learnings & Gotchas (長期記憶へ移行推奨)

### OpenAI Realtime Translate API
- session.update は厳密、未対応パラメータで全体拒否
- input transcription は明示有効化が必要（`audio.input.transcription.model`）
- 原文/翻訳は別レートストリーム、ペアリング前提の UI は破綻

### Cookbook が SPEC より正確な場合がある
- 公式 API リファレンスに記載がなくても Cookbook には実用例が載っていることがある
- WebFetch を Cookbook URL に向けて取得する習慣を持つ

### PEP 703 free-threaded Python 対応
- unsynchronized read/write はデータ競合（GIL なしで refcount 操作も atomic でない）
- 共有状態は frozen dataclass + threading.Lock で snapshot 化が定石
- queue.Queue は「最新値だけ欲しい」ユースケースには不向き（溜まる）

### テストの flaky 原因はポート競合が頻出
- TIME_WAIT 状態のポートがテスト間で残留
- `_get_free_port()` ヘルパーで OS から動的払い出しが最も堅牢

### gitleaks の allowlist 設計
- 汎用 `-fake-` インフィックスは攻撃者が `sk-realKey-fake-...` で回避する余地あり
- 厳格な regex（プレフィックス + サフィックス + 文字種）で防御

### codex を使ったセカンドオピニオン
- 大規模リファクタや設計判断には codex CLI でセカンドオピニオンを取ると安心
- ホットパスのパフォーマンス考察、API 仕様検証で特に有用
